# ระบบโปรไฟล์และคะแนน พขร.

เก็บประวัติงานของพนักงานขับรถไว้ที่เดียว ให้ทีมงานให้คะแนนพร้อมเหตุผลหลังจบงาน
แล้วใช้ข้อมูลนั้นตอบคำถามเดียวที่สำคัญ — **งานนี้ควรจ่ายให้ใคร**

| ส่วน | เทคโนโลยี |
|---|---|
| ฐานข้อมูล + สิทธิ์ + auth | Supabase (Postgres 15+, RLS, Auth, Storage) |
| หน้าเว็บ | React 19 + TypeScript + Vite |
| โฮสต์ | Cloudflare Workers (static assets) |
| นำเข้าข้อมูล | อัปโหลด `.xlsx` ในเบราว์เซอร์ (SheetJS) + สคริปต์ Python สำหรับชุดแรก |

## เรื่องที่ต้องเข้าใจก่อนใช้งาน

### คะแนนที่แสดงไม่ใช่ค่าเฉลี่ยดิบ

ข้อมูลจริงมี พขร. 56% ที่วิ่งแค่เที่ยวเดียว ถ้าใช้ค่าเฉลี่ยตรง ๆ คนที่ได้ 5 ดาว
จากงานเดียวจะขึ้นอันดับ 1 ทันที ระบบจึงใช้สองกลไกทับกัน

```
w(r)     = 0.5 ^ (อายุรีวิวเป็นเดือน / 6)        ครึ่งชีวิต 6 เดือน
adjusted = (m × 5 + Σ sᵢ·wᵢ) / (5 + Σ wᵢ)       m = ค่าเฉลี่ยทั้งระบบ
```

ผลคือ 5.00 จากงานเดียวจะแสดงราว 4.2 ส่วน 4.61 จาก 37 งานจะแสดง 4.42

### รับไฟล์ได้หลายรูปแบบ ไม่ต้องแก้โค้ด

ไฟล์งานจริงมีหัวตารางอย่างน้อยสามแบบที่หมายถึงสิ่งเดียวกัน

| ฟิลด์ | ALLMANUAL | EXPRESS | MASTER |
|---|---|---|---|
| ชื่อ พขร. | `ชื่อพขร` | `ชื่อ พขร.` | `ชื่อพขร` |
| เบอร์โทร | `เบอร์โทรพขร.` | `เบอร์โทรพขร.` | `เบอร์โทร` |
| เส้นทาง | `เส้นทาง (Route)` | `เส้นทาง / ดรอป / จำนวนลัง` | `เส้นทาง (Route)` |
| ราคารับ | `ราคารับ` | `ราคาวางบิล` | `ราคารับ` |
| ราคาจ่าย | `ราคาจ่าย` | `ค่าเที่ยว พขร.` | `ราคาจ่าย` |
| ลูกค้า | `ประเภทงาน` | `ประเภทงาน` | `ลูกค้า` |

`apps/web/src/lib/sourceProfiles.ts` เก็บ "ชื่อที่ยอมรับได้" ของแต่ละฟิลด์ไว้เป็นรายการ
แล้วจับคู่ด้วยหัวตารางที่ตัดช่องว่างและจุดท้ายคำออกแล้ว หัวตารางที่ไม่ได้อยู่แถวแรก
ก็หาเจอ (ไล่หาแถวที่จับคู่ฟิลด์ได้มากที่สุดใน 8 แถวแรก) การเพิ่มรูปแบบใหม่คือการเติม
ชื่อลงในรายการ ไม่ต้องแตะตรรกะการนำเข้า

`scripts/etl_excel.py` ใช้ตารางชื่อชุดเดียวกันนี้ทุกบรรทัด

### การนำเข้าซ้ำไม่ทำให้ข้อมูลซ้ำ

ทุกเที่ยวมี `row_hash` = SHA-256 ของ (วันที่, ลูกค้า, ทะเบียน, เบอร์ พขร., เส้นทาง, ราคารับ, ราคาจ่าย)
และทุก id เป็น UUID v5 ที่คำนวณจากคีย์ธรรมชาติ อัปโหลดไฟล์เดิมซ้ำจึงได้ **เที่ยวใหม่ 0**

### เที่ยวที่เหมือนกันทุกช่อง แต่เป็นคนละเที่ยว

แถวที่คีย์ธรรมชาติซ้ำกันเป๊ะ มีได้สองความหมาย ต้องแยกให้ออก ไม่งั้นจะผิดทางใดทางหนึ่ง

**ก) เที่ยวเดียวกันที่ถูกคัดลอกไปหลายชีต** — ชีต `IMPORT SUM B2C DATA EXPRESS`
คือ `ALLMANUAL` ต่อกับ `Import-Month-Now2025` งานเดือนล่าสุด 454 แถวจึงอยู่สองรอบในชีตเดียว
ถ้านับตรง ๆ จะได้เที่ยวเกินมา 454 เที่ยว

**ข) คนละเที่ยวจริง ๆ ที่บังเอิญเหมือนกันหมด** — นพพล เสนาบูรณ์ วิ่ง
`JTC - ท่าเรือ KERRY แหลมฉบัง` สามเที่ยวในวันที่ 20 ก.ค. ราคาเท่ากันทั้งสามเที่ยว
ต่างกันแค่ลำดับงาน 13 / 14 / 15 (บางคู่ยังมีเลขตู้ต่างกันในหมายเหตุด้วย)

ตัวแยกคือคอลัมน์ **ลำดับงาน** ลำดับงานเท่ากัน = แถวเดียวกันที่ถูกคัดลอก
ลำดับงานต่างกัน = คนละเที่ยว จึงนับแบบนี้

1. ในแต่ละชีต ยุบแถวที่คีย์ตรงกันและลำดับงานตรงกันให้เหลืออันเดียว
2. จำนวนเที่ยวจริงของคีย์หนึ่ง = ค่ามากที่สุดที่ชีตใดชีตหนึ่งนับได้
3. เที่ยวที่ 1 ใช้ hash สูตรเดิม เที่ยวที่ 2 ขึ้นไปต่อท้ายด้วย `|#n`

ข้อ 3 สำคัญ — เที่ยวแรกได้ hash เท่าสูตรเดิมทุกประการ ข้อมูล 7,500 เที่ยวที่โหลดไปแล้ว
จึงยังตรงเหมือนเดิม ไม่ต้องล้างฐานข้อมูล (ยืนยันแล้ว: hash เดิมตรง 7,500/7,500 หายไป 0)

ผลกับไฟล์จริง: จาก 8,010 แถวที่ใช้ได้ เหลือ 7,556 เที่ยว โดยทุกชีตนับตรงกันหมด
ไม่มีคีย์ไหนที่ชีตนับไม่ตรงกันเลย และได้เที่ยวจริงคืนมา 8 เที่ยวที่เดิมถูกทิ้งเพราะนับว่าซ้ำ

### ข้อจำกัดที่รู้ตัว: ค่าใช้จ่ายเพิ่มถูกนับเป็นอีกเที่ยว

บางงานถูกบันทึกเป็นสองบรรทัดในลำดับงานเดียวกัน บรรทัดแรกเป็นค่าเที่ยว
บรรทัดที่สองเป็นค่าเสียเวลา ค่าค้างคืน หรือค่าล่วงเวลา เช่น

```
12/08/2026  ลำดับงาน 7  นพพล เสนาบูรณ์  TIPS CD1 - สมุทรสงคราม  13,500
12/08/2026  ลำดับงาน 7  นพพล เสนาบูรณ์  TIPS CD1 - สมุทรสงคราม   1,500  "ค่าเสียเวลา 08.15 - 15.07"
```

ระบบนับเป็นสองเที่ยว ทั้งที่เป็นงานเดียว เพราะแยกกรณีนี้ออกจาก "ราคาถูกแก้ย้อนหลัง"
ไม่ได้แน่นอน จึงเลือกที่จะ**ไม่เดาแทนผู้ใช้** แต่รายงานไว้บนหน้าอัปโหลดพร้อมรายการ
ในไฟล์จริงมี 49 งาน คิดเป็น 0.6% ของเที่ยวทั้งหมด — ถ้าอยากให้ตรงเป๊ะ
ให้รวมยอดในไฟล์ต้นทางเป็นบรรทัดเดียวก่อนอัปโหลด

### เมื่อไฟล์ต้นทางถูกแก้ย้อนหลัง

ถ้าฝ่ายบัญชีกลับไปแก้ทะเบียนหรือราคาของเที่ยวที่นำเข้าไปแล้ว เที่ยวนั้นจะกลายเป็น
เที่ยวใหม่ในสายตาระบบ ส่วนเที่ยวเดิมยังค้างอยู่ — กลายเป็นสองเที่ยวจากงานเดียว
หน้าอัปโหลดจึงตรวจให้ด้วย โดยเทียบ (พขร., วันที่, เส้นทาง) กับงานที่มีอยู่
แล้วรายงานว่าเที่ยวไหนน่าจะเป็นของเดิมที่ถูกแก้ และต่างกันตรงช่องไหน

ในไฟล์ IMPORT SUM พบ 10 เที่ยวแบบนี้ ทั้งหมดเป็นการเติมทะเบียนรถย้อนหลังในงาน DD

### Python กับ TypeScript ต้องให้ค่าตรงกันทุกแถว

การโหลดชุดแรกทำด้วย Python ส่วนการอัปโหลดรายเดือนทำในเบราว์เซอร์
ถ้าสองฝั่งคำนวณต่างกันแม้แถวเดียว เที่ยวเดิมจะถูกนำเข้าซ้ำโดยไม่มีใครรู้

`verify_parity.mjs` ไม่ได้ถือสำเนาตรรกะไว้เอง แต่แปลง TypeScript **ตัวจริง**
ด้วย esbuild แล้วเรียกฟังก์ชันเดียวกับที่หน้าเว็บเรียก การทดสอบจึงไม่มีทางเพี้ยนจากของจริง
ให้รันทุกครั้งที่แก้ `normalize.ts`, `cleaning.ts`, `sourceProfiles.ts` หรือ `etl_excel.py`

```bash
node scripts/verify_parity.mjs "IMPORT SUM ALL DATA DAILY B2B EXPRESS .xlsx"
python scripts/validate_csv.py      # ตรวจ FK / CHECK / ชนิดข้อมูล ก่อนโหลดเข้า DB
```

> **เคยพังมาแล้ว** — SheetJS คืนวันที่เป็นสตริง `"2025-01-10 00:00:00"` ซึ่ง
> `new Date()` ตีความเป็นเวลาท้องถิ่น พออ่าน component แบบ UTC กลับในเขตเวลา
> UTC+7 จะได้ `2025-01-09` **เลื่อนไป 1 วันทุกแถว** ทำให้ hash ไม่ตรงกัน
> 7,446 จาก 7,500 แถว ตอนนี้แก้แล้วโดยให้ SheetJS คืนเลข serial ของ Excel
> (`cellDates: false, raw: true`) แล้วแปลงด้วยเลขล้วนโดยไม่ผ่านเขตเวลา

### การระบุตัวตน พขร.

เบอร์โทรอย่างเดียวใช้เป็นคีย์ไม่ได้ ในข้อมูลจริงมี

- **80 เบอร์** ที่ผูกกับหลายชื่อ — บางอันสะกดผิด (`พีระพัฒน์ หุ่นลำพู` / `พีรพัฒน์ หุ่นลำภู`)
  บางอันเป็นคนละคนจริง ๆ ที่ใช้เบอร์กลางของผู้รับเหมา
- **87 ชื่อ** ที่มีหลายเบอร์ — เปลี่ยนเบอร์

ระบบจึงใช้คีย์ `(เบอร์, ชื่อ)` แล้วรวมชื่อที่คล้ายกันเกิน 72% บนเบอร์เดียวกันเข้าด้วยกัน
ชื่อสะกดอื่นถูกเก็บไว้ในตาราง `driver_aliases` ให้ค้นหาเจอ
จากข้อมูลชุดแรกรวมได้ 40 รายการ เหลือ พขร. 1,289 คนจากคู่ดิบ 1,329 คู่

### ข้อมูลส่วนบุคคล

เลขบัญชีธนาคารและชื่อผู้รับโอนอยู่ในตาราง `driver_private` แยกออกมา
RLS เปิดให้เฉพาะ `hr` และ `admin` — ต่อให้เผลอ `select *` ที่หน้าเว็บก็ไม่หลุด

ไฟล์ `.xlsx` ต้นฉบับและโฟลเดอร์ `data/out/` ถูก ignore ใน git แล้ว

### การเปลี่ยนสถานะทิ้งร่องรอยเสมอ

สถานะเป็น **ตัวกรองแข็ง** ในการจัดอันดับ — ตั้งเป็น `inactive` หรือ `blacklisted`
แล้วคนนั้นจะหายจากหน้า “หาคนสำหรับงาน” ทันที ซึ่งกระทบรายได้ของเขาโดยตรง

- สองสถานะนี้ **บังคับกรอกเหตุผล** อย่างน้อย 10 ตัวอักษร (CHECK constraint ที่ฐานข้อมูล)
- ทุกการเปลี่ยนถูกบันทึกลง `driver_status_history` โดย **ทริกเกอร์** ไม่ใช่โดยแอป
  ต่อให้มีใครไปแก้ผ่าน SQL Editor ตรง ๆ ร่องรอยก็ยังถูกเขียน
- ตารางประวัติไม่มี policy `insert`/`update`/`delete` เลย แอปเขียนเองไม่ได้
- เปลี่ยนกลับเป็น `active` ได้ทุกเมื่อ ประวัติงานและคะแนนเดิมไม่หาย

### คะแนนลบไม่ได้

ไม่มี RLS policy สำหรับ `delete` บนตาราง `driver_ratings` เลย ลบไม่ได้ทั้งระบบ
แก้ไขได้ภายใน 24 ชั่วโมงเท่านั้น ถ้ามีข้อโต้แย้งให้ admin ใช้การ void
ซึ่งเก็บว่าใครยกเลิกและเมื่อไร

`validate_csv.py` ตรวจคีย์ซ้ำ, foreign key ทุกเส้น, CHECK constraint ทุกข้อที่เขียนไว้
ใน schema, ชนิดข้อมูล, ความถูกต้องของ uuid5 และการ escape ใน CSV

**ยังไม่ได้ทดสอบ** — ยังไม่มีโปรเจกต์ Supabase จริงให้ยิง จึงยังไม่ได้รัน migrations
กับฐานข้อมูลจริง และยังไม่ได้ทดสอบ RLS ด้วยผู้ใช้จริงแต่ละบทบาท

**ยังไม่ได้ทำ**

- Cloudflare Worker สำหรับ cron (แจ้งเตือนงานค้างให้คะแนน / ใบขับขี่ใกล้หมดอายุ)
- อัปโหลดเอกสารและรูปเข้า Supabase Storage
- หน้าจัดการผู้ใช้และสิทธิ์ (ตอนนี้แก้ที่ตาราง `profiles` โดยตรง)
- ส่งออก Excel
- บันทึก `outcome` / `on_time` รายเที่ยว (ข้อมูลนำเข้าถือว่าสำเร็จทั้งหมด
  ส่วนคะแนน “ตรงเวลา” ในสูตรจัดอันดับจึงยังใช้ค่าเริ่มต้น 0.8 เท่ากันทุกคน)
